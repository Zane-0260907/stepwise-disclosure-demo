# V9 开发检验：未通过扩大实验的门槛

这是一份候选方法的开发结论，不是第九版论文，也不是达到 8 分的声明。用户已明确本轮仅用 DeepSeek；没有跨模型验证。

## 实际完成

- 实现本地类型化视图、筛选、排序、聚合、文本检索、会话内引用、延迟返回及来源版本检查。
- 所有主对照均能通过 `execute_plan` 一次执行本地查询，只返回最后选定的列；不能故意让强基线先发送原始全表。
- 24 个开发任务：8 个基于 tau 零售数据库的派生只读问题、8 个基于 tau 航班数据库的派生只读问题、8 个 CUAD 原始合同问题。前两组不是原始 tau 多轮事务任务，亦非其完整基准成绩。
- 三方法共 72 次完整开发尝试，202 次实际 DeepSeek 调用，1,001,032 tokens。之前三例诊断另外保存，9 次运行、44 次调用、193,778 tokens；还有一次仅返回 OK 的连通性探针，9 tokens，不属于实验。所有失败保留。
- 验证器重执行所有本地工具，检查冻结源码、请求/响应摘要，并将每个调用匹配到一个不同的供应商传输记录。匹配记录和代码公开，密钥不包含在材料中。

## 为什么不继续扩大

最初三个诊断例中，航空表仅给了 `departure` 时间字段，缺少清楚的起终点表示；模型将它误解为出发机场。补齐 `origin/destination/departure_time` 与类型后重新命名开发批次，原诊断记录、输入与代码均保留。

更关键的设计问题是：对于当前登记的纯查询流水线，强基线可以把筛选、排序、聚合一起在本地执行，只返回末端结果。延迟共享只是另一种求值与返回时机；在没有中间外部观测时，二者能实现相同输入输出与披露。24 个案例中，所有方法首个动作均为 `execute_plan`，说明这个强基线实际被使用。不能把查询融合或延迟求值重新命名为独立算法创新。

合同中，强基线一次达到调用上限；延迟共享一次收到非单工具格式响应，并在另一个任务耗用完整十轮。词法检索和文本充分性没有解决。有限代码测试证明执行行为，不会把这些语义问题变成正确答案。

因此 B 门槛未通过，C/D 正式大样本不启动，E 正文与 UI 不切换到此候选。稳定的 v8 论文和演示保留。当前任务没有达到实验 8 分、技术贡献 8—8.5 的研究目标。

## 新证据要求

下一种候选机制必须首先展示：在允许强基线使用同样本地查询能力时，仍有它无法等价处理的实际需求。合理候选的作用范围应来自真实多轮任务、跨接收方任务约束或无法精确本地计算的语义步骤；不能故意禁止基线的查询融合来构造优势。在证明具体差异前，不追加新的复杂算法、大批调用或论文包装。

同时需要将开发任务替换或扩展为真正的原始多轮环境；当前只读派生问题只够测试接口，无法承担最初方案要求的完整智能体实验。这个差距属于本轮实现未完成项，不应写成已验证的动态任务泛化。
