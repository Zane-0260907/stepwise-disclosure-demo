# V10 原始多轮业务任务开发核查

本轮目标仍为：在运行时决定步骤的执行位置和给当前接收方的输入，技术贡献达到 8—8.5 分、实验说服力至少 8 分。**本轮接通了原始多轮业务环境，但尚未达到这一研究验收目标。** 不能把 6/6 的一次开发结果、更多 API 调用或参数脱敏重新解释成联合选择机制的创新。

## 已实现什么

采用 tau2-bench 固定提交 `b7ea9074c1cba482b30687fecdb5c8425fd6f619` 的原始零售、航空任务、政策、数据库和 Python 业务工具。原工具会真实修改本地内存中的订单、退款、预订和乘客记录；不是预填结果，也不操作真实订单。适配器仅绕过上游根包的可选语音依赖。对话循环和 DeepSeek 用户模拟器是本项目实现，故不称官方完整评测。

从原 train 划分按固定哈希顺序选择六个有状态修改的任务，按客户场景去重。任务的原始指令未改写；参考动作仅用于离线状态评价和开发样本的写操作资格筛选，不进入模型提示或执行器。六个任务在多轮开发中反复使用，**只有六个来源任务，54 次尝试不是 54 个独立样本**。

完整记录包括 10 个开发批次、54 次尝试、952 次实际 DeepSeek 调用和 4,485,819 tokens。调用按云端规划器、对话用户模拟器、本地确认用户模拟器分别保存。每次调用匹配一个不同的供应商载荷/响应记录；代码快照、失败和诊断批次全部保留。

新增的本地确认执行层解决了一个实际接口问题：云端可以引用已有记录中的地址，本地再解析完整参数、展示给用户并获得同意，随后调用原业务函数。拒绝、状态变化、重复确认均不会执行。该能力同时提供给所有对照，不作为本项目首次提出的算法。

## 开发过程暴露的问题

1. 第一版适配器遇到多个工具调用就终止，与上游顺序执行行为不一致。修正为顺序执行，并保留格式违规标记。原失败批次没有覆盖。
2. 仅把地址替换成引用时，模型不能向用户确认具体地址，转交人工。加入共同的本地确认层后，原始地址更新任务可以完成三笔订单和默认地址的更新。
3. 用户模拟器曾因一个确认面板只显示一笔操作而拒绝全部请求。共同确认说明补充了“这是多步任务中的一个原子操作”；明确要求原子性的场景仍可拒绝。三方法随后使用同一说明复跑。
4. 多个航空结果虽然显示完成，却漏掉取消原预订，或者执行了取消而非改舱。最终数据库比较能发现这些错误，HTTP 200 和界面的完成标记不能发现。

## 最后一次匹配开发比较

三方法共用原始业务工具、本地确认能力、模型、六个任务和调用上限。完整上下文返回原值；普通引用基线可在执行前还原字段；受限引用另外检查源字段仍有效且使用位置符合登记用途。后两者均隐藏 `address1/address2/zip/email/last_four/dob` 六类工具返回字段，不是自动语义最小化。

| :-- | --: | --: | --: |
| 最终数据库与参考动作一致 | 5/6 | 4/6 | 6/6 |
| 规划器调用 | 61 | 67 | 67 |
| 对话用户模拟调用 | 37 | 43 | 40 |
| 本地确认模拟调用 | 12 | 12 | 14 |

| 已发送工具回复中的六类字段原值条目 | 111 | 0 | 0 |
| 因引用用途或源值检查拒绝的操作 | 0 | 0 | 0 |

字段条目按不同工具消息计数，不是不同敏感事实数、隐私风险或不必要披露比例。用户在聊天中主动提供的邮箱等内容不属于这个工具回复指标。引用可能增加 token 和字节；不能宣称整体带宽更省。

**6/6 不能证明受限检查带来正确率增益。** 这批轨迹没有任何一次引用检查改变执行路径。固定规划器提出的动作、引用和用户确认后，移除额外检查会得到相同原生工具调用。不同运行之间的任务差异包含模型与模拟用户轨迹的变化，不能归因于未触发的机制。普通引用基线已达到相同的六类工具字段隐藏结果。

后续已实际实现上述干预：普通引用和受限引用两组共 12 条轨迹、107 个动作，分别在两个全新原始业务数据库中重放。固定模型提案与确认后，两侧每一步业务调用、返回值与最终状态均相同，新增模型调用为 0。这个结论仅针对已观察轨迹，不证明所有输入都等价。逐动作证据见 [paired-replay.json](../evidence/development-v10/paired-replay.json)；已有工作重合与研究关口决定见 [机制验证](mechanism-gate.zh-CN.md)。

三组还分别记录 28、29、31 条多工具或文本与工具混合的响应形态警告。其业务含义需要独立检查；本轮分数只表示完整数据库与参考动作的严格一致，既不覆盖自由文本语义，也不等于官方 tau2 reward。某些不同的最终状态也可能需要人工判定，不能直接叫任务语义错误。

## 可信域和评价边界

生产设计中的确认用户是本地的人。本轮为自动化测试，让同一个 DeepSeek 模拟这个用户，确认请求会包含本地完整参数。这些调用和原值均公开计入评价基础设施，**不能据此声称供应商全程看不到原值**。公开任务中的数据来自上游基准；这一设置不是生产隐私验证。

源值、工具输出、实际请求和最终状态可离线核验。确认用户的判断是否合理、对话是否满足业务政策仍待真人评阅。没有完成的人审不记分，没有独立测试集结论，没有跨模型结论。

本轮只接通真实多轮工具和本地执行参数绑定，**没有新增执行位置与信息表示的联合选择算法**。核心论文仍是原来的研究问题；不能把这些诊断任务替换成新的 PII 脱敏主题。

固定轨迹的强基线检查已完成，现有候选没有展现额外收益。后续应在相同查询、确认和授权能力下提出可检验的方法差异，再做受控比较。此前“基线理论上无法等价处理”的要求过强：算法改进可以体现为同等能力下的更好选择，并不要求增加表达能力；但若基线已使用相同优化并产生相同结果，就不能宣称新增收益。若没有这一差异，应明确收缩为系统工程演示，不能靠更换 JS、扩展几百次调用或自评高分解决新颖性。这里列的是尚未完成的研究任务，不是已证明可实现的增益承诺。

稳定 Word 与 UI 保持原版本；新增代码和记录放在独立开发分支，不覆盖商业项目。V10 尚不是可投稿成稿，也不满足本轮约定的分数目标。
